# 规划规范

> PRD 和计划文件格式约定。所有新增或重大变更需在 `.omo/plans/` 下编写 PRD。

---

## PRD 模板

```markdown
# PRD: [功能标题]

## 背景与动机
- 为什么需要这个功能？
- 解决什么问题？
- 用户场景描述

## 范围
### In Scope
- [ ] 功能 A
- [ ] 功能 B

### Out of Scope
- 本次不做的内容

## 技术方案
- 涉及模块（core/shared/plugins/which）
- 数据模型变化
- API 设计（Provider 签名、路由变化）
- UI 变化（新增页面/组件）

## 数据模型
- 新增表 / 修改字段
- schemaVersion 变更
- 迁移逻辑

## UI 变更
- 新增页面/组件
- 路由变化
- 响应式布局方案

## 测试计划
- [ ] 单元测试覆盖数据层
- [ ] Widget 测试覆盖 UI
- [ ] 集成测试覆盖用户流程

## 验收标准
- [ ] `flutter analyze` 通过
- [ ] `flutter test` 通过
- [ ] UI 在桌面端（≥720px）和移动端均正常
- [ ] 与现有功能不冲突
```

---

## 文件命名约定

```
.omo/plans/
├── prd-{feature-name}.md        ← PRD 文档
├── plan-{feature-name}.md       ← 实现计划（PRD 确认后拆分）
└── ...
```

- `prd-` 前缀 = 需求定义阶段，讨论用
- `plan-` 前缀 = 实现计划阶段，确认后可执行
- 文件名使用 kebab-case

---

## PRD 写作要求

| 规则 | 说明 |
|------|------|
| 语言 | 中文（按根 AGENTS.md 要求） |
| 长度 | 完整但不冗长，200-500 字为宜 |
| Scope | 必须明确 In/Out，防止范围蔓延 |
| 技术方案 | 指明实现路径，不需要完整代码 |
| 验收标准 | 必须可验证（通过/不通过） |

---

## 最小 PRD 速查

如果觉得模板太长，至少包含以下三项：

1. **做什么** — 一句话描述
2. **改什么** — 涉及的文件/模块列表
3. **怎么验证** — 判断做完了的标准
